# Debug Session: external-python-camera-binding

Status: OPEN

## Симптом

- При `ip = 192.168.4.1` внешний Python не управляет стоковым дроном.
- При `ip = 127.0.0.1` создается новый внешний дрон, который управляется.
- Видео из камеры этого внешнего дрона сильно фризит.
- Окно камеры открывается с неправильными пропорциями, вероятно из-за неверно передаваемого размера кадра.

## Ожидание

- Внешний Python должен привязываться к уже существующему стоковому дрону при корректных параметрах подключения.
- Новый `external_*` дрон не должен создаваться, если есть подходящий стоковый дрон.
- Камера должна отдавать кадры корректного размера и без заметных фризов сверх разумной задержки bridge.

## Фальсифицируемые гипотезы

1. Bridge не сопоставляет `192.168.4.1` со стоковым дроном из-за рассинхронизации connection metadata между UI state и событиями внешнего Python.
2. Для камеры используется отдельный binding key с `connectionMethod='camera'`, из-за чего камера и полетный канал оказываются привязаны к разным drone state.
3. Размер FPV-кадра берется из неподходящего canvas или из canvas с временно неверными размерами, поэтому OpenCV получает узкое изображение.
4. Основной вклад во фризы дает повторный цикл `browser render -> data URL -> HTTP state -> Python decode`, а не сам OpenCV.
5. При `127.0.0.1` новый дрон создается закономерно, потому что binding намеренно не матчится со стоковым `192.168.4.1`, и это поведение маскирует реальную ошибку привязки для стокового адреса.

## Доказательства Pre-Fix

- В `pre-fix` логах для `127.0.0.1` camera binding не матчился на стоковый `drone_1` с `ip=192.168.4.1`, поэтому создавался новый `external_*` дрон.
- В тех же логах после создания `external_*` дальнейшие `udpout` события с `127.0.0.1:8001` уже матчились именно на этот новый внешний дрон.
- Для `192.168.4.1` в браузерный binding resolution не попадали соответствующие `Pioneer`-события, что согласуется с исходным поведением patched `Pioneer`: он сначала вызывал реальный `super().__init__()` и реальные `super().arm()/takeoff()`, то есть пытался работать как обычный SDK-клиент, а не как чистое зеркало bridge.
- Внешний camera/state bridge обновлял состояние в цикле `pollExternalBridge()` раз в `250ms`, что ограничивало поток примерно до `4 FPS` даже без учета encode/decode.
- Размер FPV-capture в Python bridge зависел от размеров текущего UI canvas; при патологическом размере canvas OpenCV получал искаженный по аспекту кадр.

## Внесенные Изменения

- `python_bridge/pioneer_browser_bridge_runtime.py`: `BrowserMirroredPioneer` переведен в режим чистого browser-bridge mirror без вызова реального `pioneer_sdk.Pioneer` сокета и без реальных `super().arm()/takeoff()/...`.
- `python_bridge/pioneer_browser_bridge_runtime.py`: добавлены browser-state getters для `get_local_position_lps()` и `get_autopilot_state()`, чтобы mirrored экземпляр не зависел от реального MAVLink.
- `public/modules/python/external-bridge.ts`: частота polling для активных внешних binding повышена до `75-100ms` вместо фиксированных `250ms`.
- `public/modules/python/pioneer-js-bridge-camera.ts`: захват FPV-кадра получил защиту от патологических размеров canvas и fallback на стабильный `16:9` размер `1280x720`.
